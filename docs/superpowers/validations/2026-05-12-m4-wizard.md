## Findings

### Finding 1 — Severe flicker during streaming generation

The streaming preview flickered hard during both initial generation and iteration. Loading a more friendly progress state and showing the finished artifact only on `done` would be a better UX than the live `srcDoc` preview.

**Severity:** High
**Resolution:** Fixed — replaced the live `srcDoc` iframe with a `GeneratingPane` progress component during the streaming + image-compositing phases. The completed artifact lands as a stable `/preview/<id>` iframe on `done`.

**Root cause:** Every SSE delta triggered a `setState` that pushed new HTML into the iframe's `srcDoc` attribute. Each `srcDoc` swap tears down the iframe document and re-parses from scratch — including re-fetching every external resource (fonts, images) the artifact references. With deltas firing dozens of times per second (throttled to 5fps still ≈ 150 reparses over a 30s stream), the visible result was severe flicker plus thousands of aborted font requests in the network panel.

**The fix preserves**: the SSE stream itself still runs (we still get the `done` event with the final HTML, artifact id, and usage stats). What changed is purely the visualization — instead of progressively rendering the partial HTML, the user sees a two-phase progress indicator ("Streaming HTML" → "Compositing images") and the final stable preview drops in once.

### Finding 2 — Checkpoint name modal flashed open and closed

Clicking the "Name" / "Rename" button on a history row caused the modal to briefly appear and then disappear immediately, with no way to actually edit the name.

**Severity:** High (blocks the checkpoint-naming feature entirely)
**Resolution:** Fixed — the modal's effect now listens for the dialog's `'cancel'` event (Esc-only) instead of `'close'`, and the Cancel/Save/backdrop handlers call `onClose` directly rather than going through `dialog.close()`.

**Root cause:** Subtle StrictMode interaction. In dev, React intentionally double-invokes effects (setup → cleanup → setup) to surface bugs. My cleanup called `dialog.close()`, which queued a `'close'` event as a microtask. React's artificial remount ran synchronously, attaching a fresh `'close'` listener. The queued event from the prior cleanup then fired against the _new_ listener, which called `onClose`, which set the parent's "which round is naming" state to `null`, which unmounted the modal — all within a single tick.

The fix removes the dependency on the `'close'` event entirely. `'cancel'` fires _only_ on user-initiated dismissal (Esc on a modal), so programmatic closes from cleanup don't echo back into the parent's state.

### Finding 3 — No way to finish without iterating 3 times

The wizard's only post-generation CTA was the Refine panel — there was no "I'm happy with this version, ship it" affordance. Users felt pushed toward iteration even when the initial generation was acceptable.

**Severity:** Medium
**Resolution:** Fixed — added a `FinishActions` panel between the preview and the Refine panel. Two options: "Open standalone" (opens `/preview/<id>` in a new tab — usable for sharing or screenshotting) and "Start a new project" (resets the wizard and navigates to `/wizard/brief`). The Refine panel still sits below for users who _do_ want to iterate.

**Note:** M5 will add proper share URLs / export. This is a minimal demo-friendly exit ramp for M4.

### Finding 4 — Hydration mismatch warnings on wizard pages

While verifying Task 14, hit a React hydration mismatch warning in the `WizardProgressBar` — server rendered some step buttons with `disabled=true`, client rendered them with no `disabled` attribute. Warning was non-functional (React patched the DOM up) but noisy and indicated a real architectural issue.

**Severity:** Medium
**Resolution:** Fixed — applied "option 2" from the diagnosis: `skipHydration: true` on Zustand's persist config plus a manual `useWizardStore.persist.rehydrate()` call from `WizardHydrator` on first client paint.

**Root cause:** Zustand persist reads from `localStorage` _synchronously_ by default (because the localStorage API itself is synchronous). That meant the very first client render saw a hydrated store, while the SSR render saw the empty initial state — the two diverged on every component that read the store (most prominently the progress bar's `disabled` derivation). With `skipHydration`, SSR and first client render both see the empty initial state (matching), and hydration kicks in on the next render after `rehydrate()` resolves. The persistence test was updated to call `await persist.rehydrate()` explicitly to mirror what `WizardHydrator` does at runtime.

## Subjective UX Notes

- The "small box → fills out" iframe pattern after clicking a history row or toggling compare is a minor visual jank — cosmetic, deferred to M7. Root cause is the double-iframe security envelope (wizard iframe → `/preview/<id>` page → inner iframe with the artifact). Cheap fix would be to drop the `key={previewArtifactId}` on the wizard's outer iframe (React updates `src` in place rather than tearing down).
- Aborted-font-fetch warnings inside the iframe (`NS_BINDING_ABORTED` for fonts.gstatic.com URLs) — cosmetic, expected given srcDoc tear-downs during streaming. With Finding 1 fixed, these largely go away because we no longer mutate srcDoc during the stream.
